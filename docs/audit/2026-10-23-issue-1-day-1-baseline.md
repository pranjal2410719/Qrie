| `0006_ledger` | Supabase roles/RLS |
| `0007_retention` | `service_role` |
| `0008_usage` | RLS |
| `0009_retention_schedule` | `pg_cron`, `service_role` |
| `0010_usage_cost_rls` | RLS |
| `0011_close_session_once` | RPC, `service_role` |
| `0012_reprice_relay_units` | RPC / seed data |
| `0013_learner_model` | RLS / Supabase schema |

**Status: not verified against a clean database (blocked).**

To apply them you need a Supabase project (or local Supabase stack) that provides
the `auth` and `storage` schemas, the `service_role`/`anon`/`authenticated` roles,
and the `pg_cron` extension. A vanilla PostgreSQL server is insufficient. This
environment had no Docker, no Supabase CLI, and the PostgreSQL installer download
returned HTTP 403, so the migrations were audited **statically only**. They were
not applied, and no claim is made that they apply cleanly.

The Fastify backend uses Postgres for exactly one thing at baseline:
`Database.healthCheck()` behind `GET /health/ready`. No route reads or writes the
schema. The tenancy/ledger/retention tables are therefore unreferenced by this
service.

## 6. LAM integration reality

Two separate integration paths exist:

1. **`supabase/functions/lam-relay/`** (Deno edge function) - the real path.
   Verifies the caller through Supabase, enforces tenant membership, signs
   server-to-server requests with `LAM_JWT_SECRET`, and forwards events /
   recommendations. Deployment per its own header comment:
   `supabase functions deploy lam-relay --no-verify-jwt` (the function performs
   its own verification). `deno check` passes.
2. **`backend/src/modules/lam-integration/client.ts`** - a typed adapter that
   signs HS256 JWTs and posts to LAM. It is **not registered on any Fastify
   route**; it is exercised only by `tests/lam_adapter.test.ts`.

Consequences:

- The Qrie backend never relays real learning evidence to LAM. `/sync/events`
  acknowledges event IDs without persistence or forwarding.
- There is no LAM service in the repository, so an end-to-end HTTP path
  (client -> relay -> LAM -> recommendation) **cannot be executed** here. Day 3
  is blocked on an external service, not on this codebase.
- The "recommendation" behaviour in the backend is a fallback stub inside the
  unused client.

## 7. Secrets, unsafe defaults, and import-time behaviour

| Finding | Severity | Baseline | This PR |
| --- | --- | --- | --- |
| Public default `JWT_SECRET` committed in `config` and `.env.example` | P0 | Any reader can forge `super_admin` tokens; verified 200 on `/api/v1/admin/school` | Production startup refuses the default; dev keeps it for zero-config boot |
| Public default `LAM_JWT_SECRET` | P0 | Same class of risk for relay calls | Production startup refuses the default |
| Default `DATABASE_URL` (`postgres:postgres@localhost`) | P1 | Silently used if unset | Production startup refuses the default |
| `POST /auth/session` mints a fixed identity with no credentials | P0 | Always on | Gated by `ALLOW_DEMO_AUTH`; forced off in production |
| Student write routes unauthenticated | P0 | `/sync/events` and `/answers` accepted anonymous callers | `authenticate` preHandler added |
| Branding returned for any `school_code` | P1 | Tenant leak / misleading UI | 400 when missing, 404 when unknown (still single-tenant hardcoded) |
| CORS `origin: true` (reflects any origin) | P1 | Any website can call the API with browser credentials | **not changed** - needs an allowlist decision |
| 4xx collapsed to 500 | P1 | Malformed JSON / unknown route reported as outage | Preserved status + RFC 7807 |
| Import-time side effects | Info | `dotenv.config()` then `configSchema.parse()` at module import; DB pool is lazy | Fail-fast retained and now produces a readable error; documented |

Import-time behaviour after this PR: `config/index.ts` still parses at import, so
a misconfigured process fails before `listen()`. That is intentional: the previous
behaviour also threw at import, but as an unreadable `ZodError`. The database pool
remains lazily created, so tests and `GET /health/live` do not need Postgres.

## 8. Coupling to Qrie-specific assumptions

- **Single school hardcoded** in `student/routes.ts` (`DEFAULT_SCHOOL_BRANDING`,
  `sch_dps_rkp`), in `teacher/routes.ts` (Class 8-A/9-B fixtures), and in
  `admin/routes.ts` (DPS Sector 4 fixture). The `schoolId` claim is echoed back
  but no data is scoped by it.
- **Demo identity hardcoded** (`std_aarav_patel`, `STD-104`).
- **Grading hardcoded** to one question (`q4`, answer 25) plus a two-option
  heuristic. Not backed by a question bank.
- **Fixtures live in route handlers**, so "multi-tenant isolation" is a JWT claim
  check, not a data boundary.
- The `docs/API_CONTRACT.md` describes endpoints and a LAM health field that do
  not exist in the implementation (e.g. `/health/ready` has no `lam_relay`;
  `/auth/session` is described as exchanging a Supabase token, which it does not).

## 10. Defects fixed in this PR

Small, reviewable commits on top of `ced7a96`:

1. **`fix(backend): reject unsafe production configuration`**
   - `DEV_DEFAULTS` object + `superRefine` production guard for `JWT_SECRET`,
     `LAM_JWT_SECRET`, `DATABASE_URL`, and `ALLOW_DEMO_AUTH`.
   - `parseConfig(env)` with a readable aggregated error.
   - New `tests/config.production.test.ts`.
2. **`fix(backend): require auth and validate student write routes`**
   - `authenticate` on `POST /sync/events` and
     `POST /learning/sessions/:sessionId/answers`.
   - `events` must be an array (400 otherwise).
   - Branding requires `school_code` (400) and rejects unknown codes (404).
   - Demo session minting gated by `ALLOW_DEMO_AUTH`.
   - `BadRequestError` added; `tests/student_branding.test.ts` rewritten.
3. **`fix(backend): map client errors to 4xx RFC 7807 responses`**
   - Fastify 4xx errors keep their status instead of becoming 500.
   - `setNotFoundHandler` returns a consistent 404 envelope.
   - New `tests/error_handling.test.ts`.
4. **`docs: add issue #1 Day 1 baseline audit`** (this document).
